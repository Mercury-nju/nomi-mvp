# 私信对话承接设计

状态：首版已落地，后续规划保留。日期：2026-10-27。适用当前本机单用户 Nomi；先规则模式，后接模型。

已实现：手动加入已知客户、页面私信读取、历史基线、增量对齐、独立会话/消息/规则决策/发送记录、建议回复、逐会话授权自动承接、人工接管、发送前状态检查、命令级幂等、未知状态恢复与人工核查。监听默认关闭，重启后关闭；采集与监听分时执行。

尚未实现：整个账号陌生私信自动发现、细粒度找客/私信公平调度、官方接入及身份映射、通用模型对话、自动结构化留资。真实页面读取已验证；真实入站到自动多轮回复仍需指定测试账号验收。下文的完整历史补查、统一双通道、客户事实提取等是后续设计，不能视作当前能力。

## 目标与原则

目标不是收到消息就回一段文字，而是可靠地知道谁说了什么、这是哪一轮、回复解决什么问题，并且确认没有串人、重复发或覆盖人工接管。

消息接入、会话事实、回复决策、发送执行必须解耦。RPA 操作页面，Agent 决定下一步；Webhook 是事件入口，不是消息来源。规则模式只能覆盖明确定义的流程，未知表达进入待处理，不能伪装通用对话能力。

## 两类接入

1. 官方通道：符合能力条件、获得权限和账号授权后，由抖音推送消息事件，调用对应官方接口回复。公开 HTTPS 接入层先按对应版本文档验签、校验订阅与账号，持久化入队后快速返回；不要在回调里等待模型或浏览器。传输重试与消息重复分别去重。不同企业号、小程序等能力的 scope、事件名和身份字段不能混用。账号当前权限尚未核验，不能视作已开通。
2. 页面通道：持久化登录会话中打开私信列表，观察 DOM 变化，并周期性核对列表和会话记录。观察器生成内部消息事件；与 Agent 同进程时直接写本地 inbox，不必绕公网 Webhook。若分开部署 RPA Worker 与服务，再通过鉴权的内部 HTTP 入口传输，支持签名、事件去重与重放保护。

建议当前 demo 先实现页面通道，同时保留统一适配器接口。官方权限申请独立推进，获批后换接入层，不重写会话核心。页面通道不承诺后台离线消息必达，需浏览器在线、会话有效且内容可见。

## 完整闭环

接入观察 → 原始事件落库 → 消息归一化/身份核对/去重 → 会话更新 → 合并用户连续发言 → 规则或模型决策 → 待发送队列 → 发送前再次检查最新状态 → 平台执行 → 回显核验 → 更新会话与客户状态。

事件落库与处理进度分离；处理失败可以重试，发送结果未知则不能盲目重发。页面操作无法与数据库组成单个原子事务，不声称端到端严格恰好一次。

## 页面观察器

- 先只接管显式启用的已知客户会话；陌生会话可展示待处理，不默认自动承接整个账号。
- 首次启用做历史基线，历史消息不逐条触发回复；已经未读的历史消息展示给用户选择是否承接。
- DOM 变化只是唤醒信号，不能直接当成新消息；虚拟列表重挂载和滚动会重复生成节点。
- 以未读/最近变更会话优先扫描，但不能只靠未读标记：人工阅读会清除标记。需要定期轮扫近期会话，恢复上线后做可见范围内补查。
- 每次核对账号与对端稳定身份、消息方向、正文、可用时间和消息标识。昵称不是唯一身份。无法确认方向或身份则不自动回复。
- 有平台消息 ID 就按账号、会话、消息 ID 去重。无 ID 时结合可见时间、方向、前后消息锚点及同文消息出现次数对齐；重复的“好的”不能按正文合并。仍有歧义进入待核实。
- 首版仅自动处理文字；图片、语音、视频等记录类型和证据，转人工，不声称已理解内容。
- 建议在线时以 5–15 秒作为初始列表核对间隔，空闲后退避，配置可调；实际延迟取决于会话数量和页面耗时，不作实时保证。模型调用不占浏览器锁。

## 对话引擎

会话控制状态：auto / human / paused / closed，另存阻塞原因（登录失效、验证、页面变化、身份不明）。业务阶段独立存储：初次回应 / 需求了解 / 方案说明 / 待人工 / 预约 / 结束，不能用“已发消息”冒充“已获线索”。

每个会话串行处理。收到一组连续发言后，用短暂可配置静默窗口合并，保留每条原文；超长持续输入设置等待上限。生成决策记录 based_on_message_id、conversation_revision、策略版本及事实来源。

规则首版包含：问候；明确业务常见问题；补问一个缺失需求字段；请求人工；拒绝/停止；无法识别。业务知识未配置时不得编造报价、效果、身份或承诺。拒绝、转人工立即停止自动发送；请求留资只能采用用户配置的业务策略，不将公开评论中的数字误当联系方式。

模型后续只替换决策器：输入近期原文、带来源的结构化事实、摘要、知识库与会话目标；输出 reply / ask / handoff / wait / close 及候选文本。摘要不能覆盖原始消息；网页和聊天里的指令均作为客户内容，不得更改权限或控制工具。

发送前重新读取：是否仍为 auto、是否出现新消息、是否已人工接管、是否超出授权范围、对端身份和会话版本是否一致。旧回复失效后重算，不能继续发送过时内容。

## 数据与幂等

新增独立实体，避免无限扩展 customers.messages JSON：

- conversations：账号、通道、对端身份、客户绑定、控制状态、业务阶段、revision、最后同步时间。
- messages：内部 ID、平台 ID（可缺失）、方向、内容类型、正文、平台时间与观察时间、证据、来源与置信度。
- inbound_events：原始事件、外部投递 ID、处理状态，负责接入重试与审计。
- decisions：基于哪组消息/版本做出的动作、策略版本、事实依据。
- outbox：发送命令 ID、decision ID、预期会话版本、发送状态与证据。
- identity_links：明确记录平台与应用作用域下身份映射。RPA 主页 sec_uid 不等于官方 open_id；无可靠绑定不得自动合并。

发送命令的重试复用同一个命令 ID；新一轮可以合法发送同样的文字。当前 `agent.py` 用“客户+渠道+正文”哈希做全局发送去重，仅适合原先单条触达，必须迁移为轮次/决策级命令幂等。默认一轮一条消息，分段发送需各自命令和回执。

outbox 状态：queued → sending → confirmed / failed / unknown。confirmed 必须绑定本次新出现的出站记录，不能看到历史同文就算成功；unknown 触发对账或人工核查，不自动再发。进程重启先恢复对账，再生成新回复。

## 浏览器调度改造

当前全程 browser_lock 包住发现任务，直播可持续 30 分钟，直接增加监听线程会造成回复饥饿。应建立单浏览器命令调度器，把搜索、单作品采集、会话扫描、发送拆成可让出的短操作，优先处理待承接消息并保留找客任务的执行进度。

同账号复用一个受管浏览器 context；找客与私信用独立 page，但所有会改变焦点/选中会话的动作由调度器协调，不启动多个进程争用同一资料目录。首版可以先用“承接期间暂停长采集”保证正确性，再做细粒度让出。不能承诺两页就能消除平台焦点与面板状态干扰。

人工点击“接管”先在数据库切为 human 并取消未发队列，再允许输入。外部手机或网页人工发言在被观察到时也应暂停 Agent；页面同步有延迟，仍有竞争窗口，不能声称完全杜绝外部并发。

## 落地顺序与验收

1. 只读收件箱：识别新消息和真实对端，导入会话；验证重复文本、滚动、刷新、离线恢复及陌生会话不误触发。
2. 辅助回复：规则建议、引用原消息、一键人工接管；多轮记录和客户阶段更新，不自动发送。
3. 单会话闭环：对明确启用的会话自动回复；验证连续输入合并、新消息使旧草稿失效、重启不重发、手机人工回复后暂停。
4. 多会话与采集并行：短任务调度、公平队列、积压提示与浏览器中断恢复。
5. 获批后增加官方适配器；接入模型后增加语义覆盖，沿用相同权限、状态和 outbox 机制。

真实验收使用用户指定的测试账号，验证 A 发问 → 当前账号接收 → Agent 回复 → A 再追问 → 结合前文回复 → 人工接管后自动停止。未经指定不向随机陌生人发测试消息。验收必须同时看双方真实页面及本地流水，不能只看 HTTP 200。

当前不需要为单机 demo 额外引入 Redis、Kafka 或 n8n：SQLite 事务队列与单 Worker 足够；达到多账号/多实例需求后再替换基础设施。公网官方回调应使用独立接入服务，不把当前无公网认证的本地工作台直接暴露出去。
